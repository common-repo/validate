# validate

A [common-repo](https://github.com/common-repo/common-repo) upstream that
adds managed-file validation without replacing a repository's custom CI.

## What consumers receive

Only [`.github/workflows/common-repo.yaml`](src/.github/workflows/common-repo.yaml).
The `Common-repo diff` job:

- Uses SHA-pinned actions and common-repo **v0.38.2** by default.
- Runs `common-repo validate`, then `common-repo diff`.
- Fails on changed or missing managed files; it does not repair them.
- Runs on pull requests, pushes to `main`, merge queues, manual dispatch,
  and reusable-workflow calls.
- Has read-only repository permissions and does not persist checkout credentials.

`common-repo apply --dry-run` can succeed while generated files differ. It
is not a substitute for the diff check. Custom build, test, release and
pre-commit workflows remain owned by their existing upstream or consumer.

## Adopt

Requires common-repo 0.38.2 or newer for local authoring. Pin a published
release; the examples use the initial tag `v0.1.0`.

Append to your `.common-repo.yaml`, after existing upstream-specific excludes:

```yaml
- repo:
    url: https://github.com/common-repo/validate
    ref: v0.1.0
```

Then run:

```sh
common-repo validate
common-repo apply
common-repo diff
```

Commit the config and generated workflow together. Check that existing
managed files are already in sync; this gate intentionally exposes any
pre-existing drift. Do not hand-edit the generated workflow.

The default push branch is `main`. Repositories with another release
branch can call this workflow from their own CI using
`uses: ./.github/workflows/common-repo.yaml` and `secrets: inherit` when
private upstreams are configured. Use a different concurrency group for
the caller, so it cannot cancel the called validation workflow.

## Private upstreams

Public-only consumers need no App secrets. For private upstreams owned by
one GitHub organization, override these values inside this repo's `with:`
pipeline. Every private upstream in the transitive inheritance chain must
be included, not just the first one.

```yaml
- repo:
    url: https://github.com/common-repo/validate
    ref: v0.1.0
    with:
      - template-vars:
          GH_APP_ID_SECRET: EXAMPLE_ORG_BOT_APP_ID
          GH_APP_KEY_SECRET: EXAMPLE_ORG_BOT_PRIVATE_KEY
          GH_APP_OWNER: example-org
          VALIDATE_PRIVATE_REPOSITORIES: internal-upstream
```

The corresponding organization/repository secrets must contain an App
client ID and private key. The App installation must have Contents read
access to the comma-separated repository names. No write permissions are
requested. The token is restricted to that list, used only for those
upstream clone URLs, and revoked by the App-token action at job completion.
Git's URL rewrite is prefix-based, but the token can only read the listed
repositories. Temporary Git credentials are mode 0600 and removed even
when validation fails. Public repositories outside the list use normal
unauthenticated access.

Fork pull requests cannot receive App secrets. If private upstreams are
configured, those runs fail closed; they must not use `pull_request_target`
or skip parity to get a green check. This template supports one private
upstream owner per consumer; multi-owner access needs an explicit design.

| Variable | Default | Meaning |
| --- | --- | --- |
| `COMMON_REPO_VERSION` | `v0.38.2` | Exact common-repo CLI version |
| `GH_APP_ID_SECRET` | `COMMON_REPO_BOT_CLIENT_ID` | App client-ID secret name |
| `GH_APP_KEY_SECRET` | `COMMON_REPO_BOT_PRIVATE_KEY` | App private-key secret name |
| `GH_APP_OWNER` | `common-repo` | Private upstream installation owner |
| `VALIDATE_PRIVATE_REPOSITORIES` | empty | Comma-separated private upstream names |

Keep the CLI version equal to the version used to generate managed files,
including the pin in a Renovate workflow that runs `common-repo apply`.

## Authors

Source lives in [`src/`](src/); only that payload is exported. The `self:`
pipeline in [`.common-repo.yaml`](.common-repo.yaml) separately installs
authoring tooling from `common-repo/upstream` and dogfoods validation.
[`.github/workflows/ci.yaml`](.github/workflows/ci.yaml) is hand-written,
excluded from that upstream, and runs lint plus the fixture tests. The
other root maintenance workflows/configs are generated by `common-repo apply`.

```sh
prek install
common-repo apply
script/test
prek run --all-files
```

Tests require Python 3, Git and the pinned common-repo CLI; no Python
packages or live App credentials are needed. They apply the local source
API to scratch consumers and verify clean parity, modified/deleted file
failures, custom-CI preservation, private-variable rendering, scoped Git
authentication and credential cleanup. They also check source/self/CI
pin parity. GitHub Actions still needs a post-publish run to verify real
App authentication and runner behavior.
